How the best engineers get working code out of Claude

A distillation of about 25 sources: Anthropic's analysis of 400,000 real Claude Code sessions, Spotify's production agent, controlled productivity trials, arXiv work on agents gaming tests, and the personal workflows of engineers who publish what actually stuck. The techniques are ranked by how much they improve correct, working code, not by how clever they sound.

Reality check first

The data says two things at once. Claude is now a real accelerator, but only for people who build structure around it. Left unchecked, agent-written code is measurably worse.

The top 10, ranked

If you adopt only these, you capture most of the benefit. The order reflects how strongly each one moves correctness, weighted by the evidence behind it.

  1. Give Claude a pass/fail check it can run itself Measured

    This is the single biggest lever. Without a check, Claude stops when the work looks done, and you become the test runner. With tests, a build, a linter or a screenshot diff, it iterates until the check passes. Boris Cherny, who created Claude Code, calls this his most important rule: it "will 2–3× the quality." Spotify's verification loop took PR success to about 80%.

    HowPut the check in the prompt ("…run the tests and fix failures"). For unattended work, make it a hard gate: a Stop hook that blocks the turn until tests pass, or a /goal condition. Ask for evidence, such as test output or the command and its result, not a claim of success.

  2. Separate thinking from typing: research → plan → implement OfficialPractitioner

    Jumping straight to code solves the wrong problem. HumanLayer's version has you review ~200 lines of plan instead of ~2,000 lines of code, which is where human attention has the most leverage. They report shipping 35k lines in one 7-hour session on a 300k-line codebase.

    HowExplore and plan in plan mode (Shift+Tab), edit the plan (Ctrl+G), then implement. Skip planning when you could describe the diff in one sentence, because it's overhead there.

  3. Write the spec first, and let Claude interview you OfficialPractitioner

    Agents are excellent at writing code and poor at guessing intent. A self-contained spec that names files and interfaces, states what is out of scope and ends with an end-to-end verification step removes most rework. Jesse Vincent's Superpowers starts every job with Socratic brainstorming for this reason.

    How"Interview me in detail using AskUserQuestion… then write the spec to SPEC.md." Then start a fresh session to implement it with clean context.

  4. Stop agents from gaming the tests Measured

    Once tests become the reward, agents sometimes change the test to agree with the bug. Spotify's judge caught agents disabling flaky tests and wandering out of scope. A check the agent can quietly edit isn't a real check.

    HowWrite or approve the failing test yourself, then block edits to test files with a PreToolUse hook while Claude implements. Keep some tests out of the agent's sight. Add property-based and mutation tests so weakened asserts get caught, and forbid skip, deleted asserts and special-cased inputs in CLAUDE.md.

  5. Review with a fresh context, not the author's MeasuredOfficial

    The session that wrote the code is biased toward it. A reviewer that sees only the diff and the original prompt catches scope creep and gaps. Spotify's judge vetoes about 25% of sessions, and about half of those then self-correct.

    HowRun /code-review, or have a subagent "review the diff against PLAN.md and report correctness gaps only". That last clause matters: reviewers told to find problems will invent some, and chasing all of them leads to over-engineering.

  6. Treat context as the scarce resource OfficialPractitioner

    Output quality degrades as the context window fills. After two failed corrections, the context is full of dead ends. A clean session with a better prompt almost always beats a long one.

    HowRun /clear between unrelated tasks. HumanLayer keeps usage around 40–60% and compacts on purpose by writing progress to a plan file. Send noisy research to subagents, and use /btw for side questions.

  7. Harness engineering: turn every mistake into a rule or a check Practitioner

    Mitchell Hashimoto's and Every's "compound engineering" rest on the same idea. Each time Claude gets something wrong, fix the system as well as the code, so the next session can't repeat it. The code is the output; the harness is the asset.

    HowAdd one line to CLAUDE.md for anything you had to say in chat. Better still, add a lint rule, a script or a hook, because hooks are guaranteed and CLAUDE.md is only advice. Keep CLAUDE.md under ~200 lines and prune what Claude already does right.

  8. Make the codebase easy for an agent to work in MeasuredPractitioner

    Fast tests shorten the loop more than switching to a stronger model. Spotify found that codebase consistency, one "golden" way to do each thing, made Claude measurably better. Strong types and descriptive error messages cut wasted tokens and confident wrong answers.

    HowKeep a fast, focused test command. Make assertion messages carry the actual value. Install a code-intelligence (LSP) plugin for typed languages. Standardize patterns so there's one example to copy.

  9. Prompt the end state, one change at a time MeasuredOfficial

    Spotify found that Claude does better with prompts that describe the end state than with step-by-step scripts. Packing several changes into one prompt uses up context and leaves partial results. Pointing at a real file beats describing a convention.

    HowName the file, the scenario and the done-check ("follow HotDogWidget.php"). State preconditions: when not to act. After a run, ask Claude what was missing from your prompt. It's well placed to tell you.

  10. Parallelize independent work only, and loop only on mechanical work Practitioner

    Boris runs about five sessions in separate git worktrees. Armin Ronacher now mostly writes loops that prompt Claude for him. He also warns that loops amplify Claude's habit of overly defensive, overly complex code. Loops shine at porting, migrations, performance exploration and throwaway prototypes.

    HowUse one worktree per independent task. For "Ralph"-style loops (the bundled plugin or /loop), define an objective done condition, scope the tools with --allowedTools, and test the prompt on 2–3 items before running on all of them.

The workflow the leaders converge on

Anthropic, HumanLayer, Every's Compound Engineering and Superpowers all name their steps differently, but they share the same skeleton. The last step is the one most people skip.

planPlan & reviewYou review about 200 lines of plan. This is where your judgment has the most leverage.
buildImplementFresh session, test-first, one step at a time, checks run after each.
verifyIndependent reviewA fresh-context reviewer compares the diff with the plan, reporting correctness gaps only.
compoundCapture the lessonEvery correction becomes a CLAUDE.md line, a hook or a test.

Who does what Measured

In a typical successful session, the human makes about 70% of the planning decisions (what to build) and Claude makes about 80% of the execution decisions (how to build it). Experts get about 12 autonomous actions out of each instruction; novices get about 5.

Anthropic, "How Claude Code is used in practice"

Course-correct early Official

Esc stops Claude mid-action. Esc Esc or /rewind restores code and conversation to a checkpoint. This makes risky attempts cheap: try, rewind, try something else. Checkpoints only cover Claude's own file edits, so they don't replace git.

Claude Code docs

Domain knowledge matters more than coding background Measured

Accountants, lawyers and managers succeed within about 7 points of software engineers. What predicts success is knowing the task well enough to frame it precisely and to know what to verify. A senior engineer new to Rust is a novice at Rust tasks.

Anthropic, 400k-session study

Learn by doing the work twice Practitioner

Hashimoto's ramp-up: do a task by hand, then push an agent until it matches your result in quality. It's slow at first, but it's how you learn where agents need guardrails. That fits METR's finding that the payoff arrives after about 30–100 hours.

Mitchell Hashimoto, "My AI Adoption Journey"

Quality guards

Layer the checks from cheapest to strictest. Spotify's production setup is the reference design: deterministic verifiers first, then an LLM judge, and nothing opens a PR until both pass.

Layered verification Measured

  • In the prompt: "run tests after implementing"
  • Across a session: /goal condition re-checked every turn
  • Hard gate: Stop hook blocks until the check passes
  • Second opinion: judge compares the diff with the original prompt
Claude Code docs · Spotify Honk part 3

Fixing the bug vs. moving the goalposts Measured

  • Reproduce bugs as a failing test first, then fix
  • Lock test files during implementation
  • Property tests pin relationships, not single values
  • Mutation testing checks that asserts still catch bugs
  • Tell the agent which tests a change affects. Pre-change impact analysis cut regressions from 6.1% to 1.8% (TDAD)
arXiv: TDAD, SpecBench, capped randomized tests

Watch for over-engineering Practitioner

Armin Ronacher's critique: today's models write code that is "too defensive, too complex, too local in its reasoning". They add fallbacks where they should make bad states impossible. Ask for the simplest design that makes invalid states impossible, and run a simplification pass (/simplify) before merging.

Armin Ronacher, "The Coming Loop"

Security is on you Measured

45% of samples introduced OWASP-class flaws, with log injection and XSS the weakest areas. Add a security-review subagent or /security-review for auth, input handling and anything touching secrets, and scan diffs before you commit.

Veracode 2026

Setup & codebase

Configuration lasts across every session. GitHub's analysis of 2,500+ agent instruction files shows what separates the ones that work.

A CLAUDE.md that gets obeyed MeasuredOfficial

  • Put the exact commands, with flags, near the top
  • Include one real code snippet showing house style
  • State hard "never" rules (never commit secrets, never touch migrations/)
  • Pin real versions ("React 18 + Vite"), not "modern React"
  • For each line, ask whether removing it would cause a mistake. If not, cut it
GitHub blog · Claude Code docs

Hooks for must-happen rules Official

CLAUDE.md is advice and hooks are guarantees. Useful ones: format after every edit (PostToolUse), block writes to protected paths (PreToolUse), and gate the end of a turn on tests (Stop). Claude can write them for you: "write a hook that runs eslint after every edit."

Claude Code docs · Boris Cherny's setup

Skills and subagents, on demand Official

Move occasional knowledge out of CLAUDE.md into .claude/skills/, which only loads when relevant. Define focused reviewers in .claude/agents/ with limited tools. Community packs such as Superpowers and Compound Engineering ship whole methodologies as plugins.

Claude Code docs · obra/superpowers · EveryInc

Build the codebase for fast feedback Practitioner

  • A test command that runs in seconds, and can run a single test
  • Types everywhere; LSP plugin installed
  • Assertion messages that include the actual values
  • CLI tools (gh, aws) over raw APIs, which is cheaper on context
  • Spotify gave its agent fewer tools on purpose, for predictability
Simon Willison · marmelab · Spotify part 2

Scaling up

Once one session is reliable, the leverage comes from running several and from loops. As output grows, the bottleneck moves to human review. Spotify now has 76% more PRs to review.

Parallel worktrees Practitioner

Run one session per independent task, each in its own git worktree, and number your terminal tabs. For writer/reviewer or test-writer/implementer pairs, give each role its own session so neither grades its own work.

Boris Cherny · Claude Code docs

Ralph loops Practitioner

Geoffrey Huntley's "Ralph is a Bash loop": feed the same prompt file repeatedly until a stated done condition holds. It now ships as an Anthropic plugin built on a Stop hook. It suits greenfield builds and ports with objective checks. Without a good check, it amplifies drift.

Geoffrey Huntley · anthropics/claude-code plugins

Fan-out migrations OfficialMeasured

/batch splits a change across 5–30 subagents, each in its own worktree with its own PR. Alternatively, loop over claude -p with scoped --allowedTools. Spotify ran a Java migration across its services in 3 days, work that used to take weeks.

Claude Code docs · Spotify 2026

Off-hours agents Practitioner

Start research, triage and high-confidence tasks at the end of the day, and review the results in the morning. Hashimoto aims to always have one agent working in the background.

Mitchell Hashimoto

Cost & model choice

Getting working code efficiently also means not spending the top model on grunt work.

Match the model to the job Practitioner

  • opusplan: the strongest model plans, a cheaper model implements
  • Sonnet is the default for most coding and for subagents
  • Haiku for high-volume mechanical subtasks, about 5× cheaper than Opus
  • A weak planner compounds mistakes, so don't skimp on planning
Claude Code cost docs · community guides

Spend fewer tokens Official

  • Lower /effort on simple tasks, the biggest speed lever
  • /clear between tasks; /compact <focus> when you keep going
  • Subagents keep file dumps out of your main context
  • A lean CLAUDE.md is paid for on every turn, so keep it short

What doesn't work

The anti-patterns that come up again and again. Several of these come from engineers who tried the popular advice and dropped it.

The kitchen-sink session

Mixing unrelated tasks in one context. Every output gets worse. Run /clear between them.

Correcting in circles

After two failed corrections, the context is poisoned. Restart with a better first prompt that includes what you learned.

The 600-line CLAUDE.md

Important rules get buried and ignored. Prune it, and turn must-follow rules into hooks.

Trusting "done"

Plausible code that misses edge cases. If you can't verify it, don't ship it.

Unscoped "investigate this"

Claude reads hundreds of files and fills the context. Narrow the question or hand it to a subagent.

Parallel agents on shared, mixed read/write work

Armin Ronacher found this chaotic. Fresh sessions plus notes written to files worked better. Parallelize only independent work.

Piles of slash commands

Also from Ronacher: preloaded prompts never became habits. Keep a few that encode real workflows, not every idea.

Chasing every review finding

Reviewers asked to find gaps always find some, and fixing them all produces defensive bloat. Filter for correctness and requirements.

Automation on untrusted input needs extra care

CVE-2026-54316 let a crafted GitHub issue slip an injected git flag past Claude Code's command validator in CI. It was fixed in 2.1.163. If Claude runs in CI:

  • stay on current versions
  • don't let untrusted issues or PRs trigger jobs that have secrets
  • run as non-root with read-only sandboxes
  • scope --allowedTools

Starter kit

Copy-paste starting points for the top techniques. Adjust the commands to your stack.

1 · Test gate (Stop hook)

In .claude/settings.json: Claude can't end its turn while tests fail. Exit code 2 blocks the stop and passes the error back to Claude. 
{
  "hooks": {
    "Stop": [
      { "hooks": [
        { "type": "command",
          "command": "npm test --silent 1>&2 || exit 2" }
      ] }
    ]
  }
}

2 · Spec interview

I want to build [brief description]. Interview me in detail using the
AskUserQuestion tool. Ask about technical implementation, UI/UX, edge cases,
concerns, and tradeoffs. Skip obvious questions; dig into the hard parts.
Keep going until we've covered everything, then write a complete spec to
SPEC.md: files and interfaces involved, what is out of scope, and a final
end-to-end verification step that proves the feature works.

3 · Test-first bug fix

Users report [symptom]. Likely location: [path]. First write a failing test
that reproduces it and show me it fails. Then fix the root cause, not the
symptom. Do not edit, skip, or weaken any existing test. Run the full suite
and paste the output as evidence.

4 · Fresh-context reviewer

Use a subagent to review the current diff against PLAN.md. Check that every
requirement is implemented, listed edge cases have tests, no test was
weakened or skipped, and nothing outside the task's scope changed.
Report only gaps that affect correctness or the stated requirements.

5 · CLAUDE.md skeleton

# Commands
- Test one file: [cmd path/to/test]   - Full suite: [cmd]
- Typecheck: [cmd]                     - Lint/format: [cmd]

# Stack
[Language + version, framework + version, DB]

# Style (one real example beats a description)
See [path/to/exemplary_file] for the pattern to copy.

# Never
- Never commit secrets or .env files
- Never edit, skip, or weaken tests to make them pass
- Never touch [migrations/ or other protected paths] without asking

# Workflow
- Reproduce bugs with a failing test before fixing
- Run typecheck + tests before saying you're done; show the output
