Reality check first

Skills measurably help, but only when an expert writes them and tests prove they help. Skills written casually or generated by the model can make results worse, and a registry is an attack surface.

+16.6 ptsaverage pass rate from human-curated skills (33.9% → 50.5%) across 86 tasks and 7,308 runs.SkillsBench
−8 to −11points from skills the model wrote for itself, which did worse than having no skill at all.SkillsBench
16 of 84tasks got worse even with curated skills. Test every skill against a baseline without it.SkillsBench
+4.1%more passing runs when a skill is split into a short root file plus references, but it hurt tasks that need exact formats or thresholds.SkillJuror
26.1%of 31,132 public skills had a vulnerability. Skills with scripts were 2.12× as likely to have one.arXiv 2601.10338
13.4%of ~4,000 audited skills had a critical issue: malware, prompt injection, or exposed secrets.Snyk ToxicSkills

The top 10, ranked

These are ordered by how much each one decides whether a skill helps or hurts.

  1. Watch it fail without the skill first (eval-first) MeasuredOfficialPractitioner

    Anthropic, skill-creator and Jesse Vincent all say the same thing: run Claude on real tasks without the skill, write down exactly where it fails, and write only enough to fix those failures. In SkillsBench, 1 in 5 tasks got worse with a skill, so a skill that hasn't been measured against a baseline might be doing harm. Vincent's rule: "If you didn't watch an agent fail without the skill, you don't know if the skill teaches the right thing."

    HowWrite at least 3 realistic eval prompts, run each with and without the skill, and compare. Keep the skill only if the with-skill runs are clearly better.

  2. The content must come from a human expert Measured

    Curated skills added about 16 points; skills the model generated for itself took away 8–11. A skill's value is the knowledge Claude doesn't already have: your internal systems, rules, gotchas and preferences. Claude is very good at formatting a skill, and it can't make up your organization's knowledge.

    HowDo the real task with Claude first, notice what context you had to supply, then ask Claude to turn that into a skill. You provide the facts; Claude provides the structure.

  3. Write the description as trigger conditions, not a summary OfficialPractitioner

    Until a skill triggers, the description is the only part Claude sees, and Claude tends to under-trigger skills. There's a less obvious trap too: if the description summarizes the workflow, Claude acts on the summary and skips the body.

    HowWrite in the third person. Say what it does and when to use it, with the actual terms users type: file types, tool names, error messages. Make it a little pushy ("…even if they don't say 'dashboard'"). Never describe the steps in it.

  4. Be concise: Claude is already smart Official

    Once loaded, every token of the skill competes with the conversation. Explaining what a PDF is, or how libraries work, is wasted. Only add what Claude couldn't know or reliably work out.

    HowKeep SKILL.md under 500 lines. For every paragraph, ask whether Claude actually needs it. Vincent aims for under 200 words for skills that load often.

  5. Split it the right way MeasuredOfficial

    A short SKILL.md that works like a table of contents, with reference files loaded on demand, raised agent use of resources from 1.2 to 3.9 per run and improved results. The exception: when success depends on exact formats, thresholds or long pipelines, the details belong in SKILL.md itself.

    HowLink reference files directly from SKILL.md and nest no deeper, because Claude may only skim nested files. Give files over 100 lines a table of contents. Organize by domain (reference/finance.md, reference/sales.md).

  6. Match the level of freedom to how fragile the task is Official

    Anthropic's analogy: on a narrow bridge with cliffs, give exact instructions; in an open field, give direction and trust Claude. A database migration gets "run exactly this script"; a code review gets heuristics.

    HowFor each step, choose: plain guidance (high freedom), a template or parameterized script (medium), or an exact command with "don't change the flags" (low). Give one default plus an escape hatch, never a menu of five libraries.

  7. Put deterministic work in scripts OfficialPractitioner

    Scripts are more reliable than code generated on the fly, and they cost almost nothing, because only their output enters context. If test runs keep writing the same helper script, that's the signal to bundle it.

    HowMake scripts handle errors instead of leaving them to Claude, explain every constant (no unexplained magic numbers), write error messages that list the valid options, and say explicitly whether to run a script or read it.

  8. Build a feedback loop into the skill Official

    "Run the validator, fix the errors, repeat" greatly improves output quality. For risky or large jobs, use plan → validate → execute: Claude writes a plan file such as changes.json, a script validates it, and only then are changes applied.

    HowGive complex workflows a copyable checklist ("- [ ] Step 3: validate") and a hard rule: "only continue once validation passes."

  9. Explain why, and test rules that enforce discipline OfficialPractitioner

    skill-creator treats frequent ALWAYS/NEVER in capitals as a yellow flag: a model that understands the reason generalizes better than one following orders. But for rules Claude is tempted to skip, like TDD or verification, Vincent shows explanation alone isn't enough.

    HowBy default, give the reason with each rule. For discipline skills, pressure-test them (deadline, sunk cost), record the excuses the agent gives, and add a counter for each one.

  10. Design for security and "no surprises" Measured

    Skills are instructions plus code running with the agent's permissions. The attacks seen in the wild: download-and-run instructions, base64 or Unicode-hidden credential theft, and instructions to disable security settings. Scripts double the risk.

    HowNo secrets in skills. Never fetch and execute remote code. Keep allowed-tools as narrow as possible. Review every script like production code. The skill should do nothing a reader wouldn't expect from its description.

The description, which decides everything

A skill that never triggers is dead weight, and one that triggers on the wrong requests is noise. Treat the description as the most-tested line in the skill.

PatternExampleVerdict
Vague"Helps with documents"Never triggers correctly
First person"I can help you process Excel files"Breaks discovery (it's injected into the system prompt)
Summarizes the steps"Use for TDD: write the test first, watch it fail, write minimal code"Claude follows the summary and skips the body
What + when + terms"Analyze Excel spreadsheets, create pivot tables, generate charts. Use when working with Excel files, spreadsheets, tabular data, or .xlsx files."Good
Pushy about when"…Use whenever the user mentions dashboards, metrics, or displaying company data, even if they don't say 'dashboard'."Counters under-triggering

Test triggering like a classifier Official

  • 20 realistic queries: 8–10 that should trigger and 8–10 that should not
  • Negatives should be near-misses that share keywords, not obviously unrelated requests
  • Messy, real phrasing: typos, backstory, file names
  • Run each query 3 times; split 60/40 into train and test; pick the best description by its test score
skill-creator's description optimizer

Know when skills don't trigger Official

Claude consults a skill only for tasks it can't easily do on its own. A simple one-step request ("read this PDF") may not trigger a perfectly described skill. Write trigger tests with realistic, multi-step requests, or they'll tell you nothing.

skill-creator: "How skill triggering works"

Writing the body

Write it like an onboarding runbook for a very capable new hire who knows nothing about your company.

Style Official

  • Use imperative instructions ("Run…", "Check…")
  • One term per concept, used throughout, never mixing "field", "box" and "element"
  • Concrete input/output examples beat descriptions of style
  • A strict template for fixed formats; a "sensible default" for flexible ones
  • No dates that will go stale; keep an "Old patterns" section instead

Structure patterns Official

  • Guide + references: quick start inline, then links to details
  • By domain: one reference file per area; Claude reads only the one it needs
  • Conditional: "Creating? → this workflow. Editing? → that one"
  • Checklist: a copyable progress list for multi-step jobs

Four types of skill, tested differently Practitioner

  • Discipline (TDD, verification): pressure-test for shortcuts
  • Technique (a method): test applying it and the edge cases
  • Pattern (a mental model): test recognizing when it applies and when it doesn't
  • Reference (APIs, schemas): test finding the right fact and using it correctly
Jesse Vincent, writing-skills

Scripts that help rather than hinder Official

  • Handle errors in the script instead of crashing and leaving it to Claude
  • Error messages list the valid options ("Field 'x' not found. Available: …")
  • Explain every constant; no magic numbers
  • Say "Run X" vs "See X for the algorithm" explicitly

Testing & iteration

The method all the strong sources share: two Claude instances, real tasks, and changes based on observed behavior rather than guesses.

The Claude A / Claude B loop Official

  • Claude A helps you write and refine the skill
  • Claude B, a fresh instance with the skill loaded, does real tasks
  • Watch B; take specific failures back to A ("B forgot to filter test accounts")
  • Repeat until B handles real work reliably

RED → GREEN → REFACTOR Practitioner

  • RED: run scenarios without the skill; record failures and excuses word for word
  • GREEN: write the smallest skill that fixes those
  • REFACTOR: find new loopholes, add counters, test again
  • This applies to edits as well: no change without a failing test
Jesse Vincent, Superpowers

Watch how Claude moves through the skill Official

  • Files Claude never opens are unnecessary or badly signposted
  • Files it always opens probably belong in SKILL.md
  • Reading in an unexpected order means the structure isn't intuitive
  • Read the transcripts, not only the final outputs

Test on every model you'll use Official

Haiku may need more guidance; Opus may find the same text over-explained. If a skill will run on several models, test on each, and use blind A/B comparisons when deciding whether version 2 is actually better than version 1.

Sanitization & prompt injection

A skill is text that Claude treats as trusted instructions, running with the user's permissions. That makes every file in the bundle, not just SKILL.md, a place to hide instructions. The research agrees that no single filter is enough, so defend in layers.

> 17%of public skills had latent injection flaws, found by a red-team/blue-team agent pair that also proposes patches.SkillSecurer

Layer 1 · Mechanical sanitization Synthesis

  • Normalize to NFKC; reject invisible, tag and bidi characters
  • Strip or flag HTML comments and raw HTML
  • Decode base64/hex blobs and re-scan them
  • Allowlist URLs and domains; reject fetch-and-run
  • Reject binaries, archives, symlinks and files outside the folder
This catches the crude attacks cheaply and runs on every commit

Layer 2 · Adversarial review Measured

  • An LLM reviewer reads the entire bundle, scripts included, and answers "what would this make an agent do that the description doesn't say?"
  • A red agent tries injections against it (the SkillSecurer approach)
  • Use two different reviewers or models, since a single scanner can be evaded
  • A human reviews the raw diff for medium risk and above

Layer 3 · Least privilege at runtime Measured

Skill-Inject's conclusion is that filtering alone fails, and context-aware authorization is needed. Keep allowed-tools as narrow as possible. Use disable-model-invocation for anything with side effects. Run scripts in a sandbox with no network unless declared, and deny access to credential paths with permission rules or hooks.

Layer 4 · Provenance & integrity OfficialSynthesis

Only publish from the registry's own repo. Sign releases, pin versions, and hash every file so any change forces a re-review. Record who approved each version. Never auto-import public skills: fork, sanitize, re-evaluate and own them.

Turning this into a registry pipeline

My synthesis of everything above, shaped for a team whose job is creating, maintaining and deploying skills. Each stage is a gate a skill must pass to move on.

  1. 1 · IntakeRecord the gap the skill fills, a named owner and backup owner, a risk tier, and the real failed tasks that justify it.owner, risk tier
  2. 2 · LintAutomatically check the schema: name and description rules, < 500 lines, references one level deep, forward slashes, no XML, fully qualified MCP names, portable fields only if it's API-bound.schema pass
  3. 3 · SecuritySanitize and scan (see Sanitization & injection): invisible Unicode, hidden HTML, encoded blobs, fetch-and-run, override phrases, secret access, biased descriptions. Then an adversarial LLM review of the full bundle, static analysis of scripts plus a sandboxed run, and a flag on broad allowed-tools.0 critical
  4. 4 · EvalsAt least 3 task evals run with and without the skill, with deterministic checks where possible. The difference from the baseline must be positive.Δ > 0
  5. 5 · TriggeringA 20-query set that includes near-misses; track precision and recall; check it doesn't collide with other skills in the registry.P/R threshold
  6. 6 · ReviewA domain expert approves the content, and a different person merges (separation of duties) for medium risk and above.2 humans
  7. 7 · ReleaseSemantic version plus changelog, signed and published through the marketplace or managed channel. Production is pinned to a version, with the previous one kept for rollback.semver, pinned
  8. 8 · OperateMonitor trigger rates and failures; review on a schedule; re-run evals when models change; deprecate stale skills.review date

Why the evals gate matters most Synthesis

SkillsBench found about 1 in 5 tasks got worse with a curated skill. A registry that deploys skills without proving they beat the baseline will ship some that make Claude worse. That's the single most important gate.

Why the security gate matters Synthesis

Public registries show npm-style supply-chain problems: 13–26% of skills have flaws, with coordinated malware campaigns in 2026. An internal registry pushes skills to many engineers at once, so one bad skill spreads widely. Treat skills as code with execution rights.

Anti-patterns

Letting Claude invent the content

Self-generated skills did worse than no skill. Claude structures; experts supply the knowledge.

A description that summarizes the workflow

Claude takes the shortcut and ignores the body. Describe when, not how.

Explaining what Claude already knows

A paragraph about what a PDF is costs tokens on every use and teaches nothing.

Offering a menu

"Use pypdf, or pdfplumber, or PyMuPDF…" Give one default and one escape hatch.

Deeply nested references

File A → B → C means Claude may only skim C. Keep references one level deep.

Wall-to-wall MUSTs

Rigid capitals without reasons generalize poorly. Explain why, and save hard rules for discipline skills you've pressure-tested.

Overfitting to your test prompts

A skill that works on only three examples is useless. Generalize from feedback instead of patching single cases.

Shipping untested edits

"It's just a small doc change" still changes behavior. Re-run the evals.

Layer-1 sanitization scanner (Python, no dependencies)

Run it in CI on every skill change: python scan_skill.py path/to/skill --allow-domain yourcompany.com. Exit 0 = pass, 2 = needs human/LLM review, 1 = block. Tested Sep 23, 2026: a test skill with 7 planted attacks was blocked (14 critical); 25 clean Anthropic skills gave 18 passes, 7 reviews, 0 blocks. It catches crude tricks cheaply and is not a complete defense (see Layers 2–4). 
"""Layer-1 sanitization scan for a skill folder.

Exit codes: 0 = pass, 2 = HIGH findings need human/LLM review, 1 = CRITICAL, block.

Usage: python scan_skill.py path/to/skill [--allow-domain example.com ...]
Catches crude injection and payload tricks cheaply. It is NOT a complete
defense: pair it with adversarial LLM review, human review, and least privilege.
"""
import argparse, base64, binascii, pathlib, re, sys, unicodedata

# Zero-width, bidi-override, word-joiner, BOM and soft-hyphen characters, plus
# Unicode "tag" characters (U+E0000-E007F), which can smuggle invisible text.
INVISIBLE = re.compile(
    "[\\u200b-\\u200f\\u202a-\\u202e\\u2060-\\u2064\\u2066-\\u2069\\ufeff\\u00ad]"
    "|[\\U000e0000-\\U000e007f]"
)
HTML_COMMENT = re.compile(r"<!--.*?-->", re.S)
B64_BLOB = re.compile(r"[A-Za-z0-9+/]{60,}={0,2}")
URL = re.compile(r"https?://([A-Za-z0-9.-]+)", re.I)
# Phrase rules can't tell *mentioning* an attack from *doing* one, so in visible
# text they are HIGH (review). The same phrase in hidden content is CRITICAL.
PHRASES = {"instruction override", "concealment from user"}
# Docs often *mention* .env or eval(); scripts actually *doing* it is the risk.
CODE_RISKS = {"credential access", "dynamic execution"}
RULES = [  # (severity, label, pattern)
    ("CRITICAL", "instruction override",
     r"ignore (all |any )?(previous|prior|above) (instructions|rules)"
     r"|disregard (the |your )?(system|previous)|you are now\b|new system prompt"),
    ("CRITICAL", "concealment from user",
     r"(do not|don't|never) (tell|inform|show|mention)[^.\n]{0,40}\buser\b"
     r"|without (asking|telling|informing|notifying) (the )?user"
     r"|without (the )?user'?s? (knowledge|consent|confirmation)"),
    ("CRITICAL", "fetch-and-execute",
     r"(curl|wget)[^\n|]*\|\s*(ba|z)?sh\b"
     r"|(iwr|invoke-webrequest|irm)[^\n|]*\|\s*iex"
     r"|powershell[^\n]*-e(nc(odedcommand)?)?\s+[A-Za-z0-9+/=]{20,}"),
    ("CRITICAL", "security disablement",
     r"(disable|turn off|bypass)[^.\n]{0,30}(sandbox|permission|security|antivirus|defender|firewall)"
     r"|dangerously-?skip-?permissions"),
    ("HIGH", "credential access",
     r"~?[/\\]\.(ssh|aws|kube|docker)\b|id_rsa|\.env\b|credentials\.json"
     r"|(aws_secret|api[_-]?key|token)\s*[:=]"),
    ("HIGH", "dynamic execution",
     r"\beval\s*\(|\bexec\s*\(|atob\s*\(|base64\s+(-d|--decode)|FromBase64String"),
]
# Checked against the frontmatter description only: the manipulation target.
PERSUASIVE = re.compile(
    r"always (use|prefer|choose) this|instead of (any )?other skills"
    r"|(most )?(official|trusted|preferred) skill", re.I)
DESCRIPTION = re.compile(r"^description:\s*(.+)$", re.M)
BINARY_EXT = {".exe", ".dll", ".so", ".dylib", ".bin", ".zip", ".7z", ".rar",
              ".tar", ".gz", ".jar", ".pyc"}


def frontmatter(text: str) -> str:
    """Return the YAML frontmatter block of a SKILL.md, or '' if absent."""
    if not text.startswith("---"):
        return ""
    end = text.find("\n---", 3)
    return text[3:end] if end != -1 else ""


def scan(root: pathlib.Path, allowed: set[str]) -> list[tuple[str, str, str]]:
    out = []

    def add(sev, where, msg):
        if (sev, where, msg) not in out:  # report each distinct finding once
            out.append((sev, where, msg))

    for f in sorted(root.rglob("*")):
        rel = f.relative_to(root).as_posix()
        if f.is_symlink():
            add("CRITICAL", rel, "symlink (may point outside the skill)")
            continue
        if not f.is_file():
            continue
        if f.suffix.lower() in BINARY_EXT:
            add("CRITICAL", rel, "binary or archive file")
            continue
        try:
            text = f.read_text(encoding="utf-8")
        except UnicodeDecodeError:
            add("HIGH", rel, "not valid UTF-8 text")
            continue

        for m in INVISIBLE.finditer(text):
            line = text.count("\n", 0, m.start()) + 1
            add("CRITICAL", f"{rel}:{line}", f"invisible/bidi/tag char U+{ord(m.group()):04X}")
        if unicodedata.normalize("NFKC", text) != text:
            add("MEDIUM", rel, "text changes under NFKC normalization (look-alike characters?)")

        if rel == "SKILL.md":
            d = DESCRIPTION.search(frontmatter(text))
            p = PERSUASIVE.search(d.group(1)) if d else None
            if p:
                add("MEDIUM", rel, f"persuasive description: {p.group()!r}")

        if f.suffix.lower() == ".md":  # comments are invisible once markdown renders
            for m in HTML_COMMENT.finditer(text):
                line = text.count("\n", 0, m.start()) + 1
                add("MEDIUM", f"{rel}:{line}", "HTML comment (hidden from rendered view)")

        is_md = f.suffix.lower() == ".md"
        hidden = [m.group() for m in HTML_COMMENT.finditer(text)] if is_md else []
        for m in B64_BLOB.finditer(text):
            try:
                decoded = base64.b64decode(m.group(), validate=True).decode("utf-8")
            except (binascii.Error, UnicodeDecodeError, ValueError):
                continue
            hidden.append(decoded)  # re-scan decoded payloads
            add("HIGH", rel, "base64 blob that decodes to text")

        visible = HTML_COMMENT.sub(" ", text) if is_md else text
        for sev, label, pat in RULES:
            vis_sev = ("HIGH" if label in PHRASES
                       else "MEDIUM" if label in CODE_RISKS and is_md else sev)
            for m in re.finditer(pat, visible, re.I):
                add(vis_sev, rel, f"{label}: {m.group()[:70]!r}")
            for chunk in hidden:  # a match inside hidden content is deliberate
                for m in re.finditer(pat, chunk, re.I):
                    add("CRITICAL", rel, f"{label} (hidden): {m.group()[:70]!r}")

        for m in URL.finditer(text):
            host = m.group(1).lower()
            if not any(host == d or host.endswith("." + d) for d in allowed):
                add("MEDIUM", rel, f"URL to non-allowlisted domain: {host}")
    return out


if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("skill_dir")
    ap.add_argument("--allow-domain", action="append", default=[])
    args = ap.parse_args()
    root = pathlib.Path(args.skill_dir)
    if not (root / "SKILL.md").is_file():
        sys.exit(f"{root}: no SKILL.md")
    findings = scan(root, set(args.allow_domain))
    for sev, where, msg in findings:
        print(f"{sev:8} {where}: {msg}")
    crit = sum(1 for s, _, _ in findings if s == "CRITICAL")
    high = sum(1 for s, _, _ in findings if s == "HIGH")
    print(f"\n{len(findings)} finding(s): {crit} critical, {high} high")
    sys.exit(1 if crit else 2 if high else 0)

Pre-publish checklist

[ ] Baseline run WITHOUT the skill recorded; failures written down
[ ] >= 3 task evals; with-skill beats baseline
[ ] Trigger set of ~20 incl. near-misses; precision/recall acceptable
[ ] Description: third person, what + when, real terms, no workflow summary
[ ] SKILL.md < 500 lines; references one level deep; ToC on long files
